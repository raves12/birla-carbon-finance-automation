# CLIENT_POC_GAP_ANALYSIS.md: client POC success criteria vs the current BCFA build (Phase 40)

Audit date: 2026-10-05. Instance `pwcmanagementservicesdemo01` (Yokohama). Branch `feature/bcfa-native-ai-completion`.

The criteria come from Birla Carbon:
- **AP:** multi-country invoice OCR; GST / VAT / withholding tax; configurable tolerances.
- **AR:** payment advice OCR; reconciliation to open items; deductions and residuals.
- **Assessment:** standard vs custom, SAP dependency, production effort.

## 1. Client sample documents

**None received yet.** The repository holds only synthetic fixtures (`test/fixtures/`):
- 6 AP invoices: India, Germany, US and Hungary vendors;
- 8 AR remittances.

All were generated by the project and are not Birla Carbon documents. No result in this phase is reported as a client-document result. Countries, layouts and accuracy for real samples stay **NOT TESTED** until the client supplies samples (`CLIENT_POC_TEST_MATRIX.md`).

## 3. Gaps against the criteria

| # | Requirement | Gap | Planned change (no new engine) |
|---|---|---|---|
| G1 | Genuine ServiceNow extraction | BCFA use cases are untrained Classic and return nothing | New BCFA **generative** use cases for AP invoices and AR payment advices, pinned to **Now LLM**, one field per value |
| G2 | Provider abstraction | Extraction is called directly from the intake service | `DocumentExtractionService` with providers `native` (DocIntel) and `simulated` (fixtures), selected by property `x_695068_bcfa.document.extraction.provider`. A failed native extraction goes to manual review and never falls back to fixture values |
| G3 | Field coverage (AP) | No tax breakdown, payment terms, country or language; no per-field confidence | Extraction contract extended with header, tax breakdown (GST / CGST / SGST / IGST / VAT / WHT) and lines, plus per-field evidence where the platform returns it |
| G4 | Country / document coverage | None | POC coverage matrix (`CLIENT_POC_TEST_MATRIX.md`), filled only from samples actually received |
| G5 | GST / VAT validation | Hard-coded country rate map | Rates move to a governed **BCFA AP Tax Expectation** decision table (country, company, tax regime). FinancePolicy reads it, and MatchingEngine stays the place where tax is compared. Outcomes: PASS, WITHIN TOLERANCE, FAIL, MANUAL REVIEW |
| G6 | Withholding tax | Not modelled | WHT expectation in the same decision table, validated against any WHT printed on the invoice. The source is labelled POC REFERENCE DATA, not SAP |
| G7 | Tolerance visibility | Rule used is returned but not stored | Store expected, actual, variance, rule and source on the AP match, exception and Playbook. Add a separate total-amount tolerance |
| G8 | AR payment advice extraction | Simulated only | Native AR use case (payer, references, UTR, amounts, invoice lines, deductions); remittance gets structured columns |
| G9 | Deduction taxonomy | 5 types | Add withholding tax, debit note, commercial, dispute, FX difference, rounding and other, with decision-table rows. Unknown or material deductions go to manual review |
| G10 | Playbooks | No tax, provider or tolerance detail | AP extraction / validation / match stages and AR extraction / deduction stages show the new fields |
| G11 | Assessment documents | None | `STANDARD_VS_CUSTOM_ASSESSMENT.md`, `CLIENT_POC_SUCCESS_REPORT.md`, `PRODUCTION_IMPLEMENTATION_ESTIMATE.md` |
| G12 | OCR accuracy | Not measured | Field-level evaluation script with ground truth per document. Synthetic fixtures are measured now and reported separately; client samples are measured when received |

## 4. Constraints carried forward

- ServiceNow-native AI only. Extraction runs on **Now LLM**; the instance-default Azure OpenAI definition is not used for BCFA.
- OCR extracts facts. Rules decide. AI explains. People approve.
- No instance-wide settings, plugin activations, ACL grants or role changes by the assistant.
- Client documents are never committed to git unless approved.
