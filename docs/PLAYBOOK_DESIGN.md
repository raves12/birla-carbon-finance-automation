## 1. Architecture

The Playbook is a view of the transaction. It is not a workflow engine.

```
Authoritative BCFA process: state models, domain services, MatchingEngine,
ApprovalEngine, IntegrationService, flows, AuditEngine
        │ every state change, AI note, exception or approval change
        ▼
FinanceJourneyService: derives journey_* fields on the invoice or payment
(stage, stage order, status, blocked because, next action, owner, ...)
        │ journey_stage_order
        ▼
Playbook stage N waits on "journey_stage_order > N" (Wait For Condition)
        │
        ▼
Guided user experience in the BCFA Workspace (platform Playbook page)
```

Rules the design enforces:

- **No Playbook activity changes data.** Only two activity types are used, and PB-UI-003 asserts this:
  - **Wait For Condition**: the stage gate.
  - **Record List**: read-only evidence.
- **No financial arithmetic in the Playbook.** Amounts come from the engines' own records:
  - `ap_match` variances;
  - `payment.allocated_amount`, `residual_amount` and `deduction_amount`, written by the allocation engine;
  - `payment_allocation` rows.
- **No completion button can advance a stage.** A stage completes only when `journey_stage_order` passes it. FinanceJourneyService sets that field from the authoritative state only.
- **Actions stay where the controls are.** Approve, resolve, request clarification and check the SAP draft are the existing UI actions on the records the evidence lists open, with their ACLs, segregation of duties (SoD) checks and audit.

## 6. Entry criteria

- A stage starts when its predecessor lane completes. Stage 1 starts with the run.
- The run starts when the invoice or payment is created (Record Create trigger).
- The exception lanes (AP 5, AR 6) start after intake and run in parallel with the processing stages.

Records created before the Playbook was activated have no run. Their journey fields are still filled by the backfill (`scripts/deploy/phase35_backfill_and_seed_bg.js`) and shown on the form and Review Summary.

## 7. Exit criteria

A stage exits only when its gate condition holds on the parent record (see the tables in section 4).

| Stage | Order is set past it only when | Source |
|---|---|---|
| Extraction | `EXTRACTED` and no open low-confidence / missing-field exception | `AP_STATE_ORDER`, `AP_REASON_STAGE` |
| Validation | `VALIDATED`/`MATCHING` and no open validation exception | as above |
| Matching | MatchingEngine moved the invoice to `MATCHED` | as above |
| Approval | ApprovalEngine moved it to `APPROVED` → posting | as above |
| Posting | `POSTED`/`RECONCILED`; never `UNKNOWN_OUTCOME` (stays 7) | as above |
| Closure | `CLOSED`/`REJECTED` (order 9) | as above |
| AR SAP processing | `CLEARED` (order 9); never `SAP_DRAFT`, `UNKNOWN_OUTCOME` or `FAILED` (stay 8) | `AR_STATE_ORDER` |

## 8. Conditional stages

Lanes support only *Immediately* and *After* start rules. Conditionality is therefore expressed through the gates:

- **Exception lanes** complete only when no exception is open and the transaction is past the exception point. A clean transaction passes them as soon as it reaches approval. A blocked one keeps them open.
- **Stages a transaction never visits** complete as soon as the order passes them. Examples:
  - an AR payment resolved by customer code without remittance correlation;
  - a rejected invoice (order 9).
- **Rejected invoices**: every stage completes, and `journey_status = rejected` on the gates says why. The Playbook does not pretend it posted: the posting list is empty and closure shows REJECTED.
- **No `conditionToRun`** is used to skip lanes. Skipping would hide the stage from the user; passing it keeps the full journey visible.

## 13. Role mapping

**Playbook permissions** are view-only for every BCFA role:

- `admin`, `ap_processor`, `ap_approver` / `ar_processor`, `ar_approver`, `finance_reviewer`, `finance_approver`, `integration_operator`, `auditor`, `read_only`;
- `admin` may also restart the run or a stage;
- no role can complete an activity by hand: gates complete only on the condition, and lists do not wait.

What each persona does from the Playbook (on the records it opens):

| Persona | Can | Cannot (enforced by the existing ACLs / SoD) |
|---|---|---|
| AP / AR Processor | resolve exceptions, request clarification, hold, request approval, classify deductions (AR) | approve own work |
| Finance Reviewer | review exceptions and AI recommendations | approve |
| Finance Approver / AP / AR Approver | approve or reject approval requests | change invoice or allocation values |
| Integration Operator | view integration transactions, reconcile, check SAP draft status | alter allocations or invoice values |
| Auditor / Read Only | view journey and evidence | any change |
| AI agent (`ai_agent`) | not in the Playbook permissions; never an approver | approve, post, clear, override |

## 14. AI integration

The AI is native Now Assist only, and advisory (`AI_GOVERNANCE.md`).

| AI input | Where it appears |
|---|---|
| Exception AI recommendation (`ai_recommendation`), Explain Exception, Recommended Next Action, Draft Clarification, AR match / residual explanation | exception list column and AI Interaction Log list in stages AP 5 / AR 6 |
| AI assistance used on the transaction | AI assistance list at closure |

- The gates never read AI output.
- The WHY of a block is the rule result, never the AI text (PB-AP-003).
- An AI recommendation to approve leaves the journey blocked (PB-AP-003).

## 15. Approval integration

- ApprovalEngine and SoD are authoritative.
- The approval stage completes only when the transaction leaves PENDING_APPROVAL / APPROVED for posting or clearing, that is, after a legitimate approved approval record and the cascade or flow.
- The approvals list shows requester, approver, group, decision, SoD check and override reason.
- The journey says who must act: "Finance Approver: requester and processor cannot approve".

## 16. IntegrationService mapping

- The Playbook never calls SAP.
- Stage AP 7 / AR 8 lists the `integration_txn` rows of the transaction: adapter, idempotency key, status, attempt, external document, unknown-outcome flag, reconciliation state, error.
- UNKNOWN_OUTCOME keeps the stage open, blocked, with the Integration Operator as owner, until reconciliation, which is never a blind retry.

## 17. SAP Draft/Direct mode

A client requirement.

**Configuration**

| Setting | Values |
|---|---|
| Property `x_695068_bcfa.ar.sap_processing_mode` | `direct` (default) or `draft`; read by `FinancePolicy.arSapProcessingMode()`; any other value is treated as direct |
| Payment field `sap_processing_mode` | captured when clearing starts; a mode already set on the payment is kept |

**DIRECT**

- `clearCustomerPayment` returns a clearing document `FB05…` (MOCK SAP).
- Allocations are cleared and open items settled.
- The payment goes to `CLEARED` → `CLOSED`.

**DRAFT**

1. MOCK SAP returns `staged: true` and a parked document `PARK…`.
2. The payment goes to the new state `SAP_DRAFT`, with `sap_status = staged_draft`. Nothing is cleared and the open items stay open.
3. **Check SAP Draft Status** confirms or rejects the draft. It is a UI action for `integration_operator`, `ar_processor`, `finance_approver` and `admin`, shown only in `SAP_DRAFT`. The job **BCFA - SAP Draft Status Check** runs it every 30 minutes.
   - It calls `IntegrationService.queryTransactionStatus`, a status query only: the instruction is never re-sent.
   - **POSTED**: allocations cleared, open items settled, `CLEARED`, then reconcile and close.
   - **Pending**: no change; the check is audited.
   - **Rejected**: AR exception, `FAILED`.

**Simulation and labels**

- `x_695068_bcfa.mock_sap.draft_outcome` controls the simulated SAP user: `pending` (default), `posted` or `rejected`. It is MOCK SAP only and means nothing to a real adapter.
- Labels everywhere say MOCK SAP:
  - the Review Summary line `SAP PROCESSING DRAFT mode | SAP status … | MOCK SAP`;
  - the Playbook stage 8 title;
  - the journey banner `SAP mode DRAFT`.

## 18. Workspace embedding

**Route**

- Route `playbook` in the BCFA Workspace (`sys_ux_app_route` "BCFA Playbook", fields `table,sysId`).
- Its screen renders the platform **Playbook** page (`sys_ux_macroponent` `32eb57e82c904510f877b925aa1a4d10`, the page Service Operations Workspace uses), bound to the route's `table` and `sysId`.

- Covered by the existing `bcfa.*` route ACL.

**Entry points**

- **Open Playbook** link on the invoice and payment forms. It only navigates; it changes no data.
- The URL above, from the workspace.

**Why a route, not a record-page tab**

The BCFA record page ("Record Default") is the platform's preset record page (SRP). Fluent cannot edit it, and editing it in UI Builder would create an instance-side variant outside source control.

**Journey on the form**

The journey fields are on the record. They can be added to the form and workspace record header without any page change (see section 19).

## 20. Audit

The Playbook adds no audit framework.

- **What is audited.** Every action reachable from the Playbook is an existing UI action or flow, already audited by AuditEngine: user, timestamp, correlation ID, decision, comment, before and after state. New events in this phase:
  - SAP_DRAFT entry (`integration_result`, reason "SAP processing mode DRAFT");
  - draft confirmed, rejected or still pending (`integration_result`).
- **What is not audited.** Journey refreshes are display updates and create no audit events (PB-AP-006).
- **Playbook runtime history.** Playbook executions are kept by the platform (`sys_pd_context`, retention 6 weeks by default).

## 21. Security

- **Data access.** The Playbook reads through the user's own ACLs. A list shows only records the user may read.
- **Run permissions.** Playbook permissions are view-only for BCFA roles (section 13).
- **Field writes.** Journey fields are read-only on the form and written only by FinanceJourneyService (`setWorkflow(false)`, no state change).
- **Actions.** No new action can approve, post, clear or override:
  - **Open Playbook** only navigates;
  - **Check SAP Draft Status** is a status query, and the `ai_agent` role cannot run it (PB-UI-005).

## 22. Errors

| Situation | Behaviour |
|---|---|
| FinanceJourneyService throws | Caught; `gs.warn('BCFA FinanceJourneyService …')`; the transaction carries on (the journey is display only) |
| Playbook not active | No run starts. The journey fields and Review Summary still show the journey; the Open Playbook page shows no run |
| Record created before activation | No run. Use the journey fields; a run can be started by an admin from Workflow Studio |
| SAP draft check on a payment not in SAP_DRAFT | Refused with a message (PB-AR-007) |
| SAP draft rejected | AR exception "SAP rejected the draft clearing document"; payment FAILED |

## 23. Troubleshooting

**A stage does not complete**

1. Check `journey_stage_order` and `journey_status` on the record.
2. If they are stale, run `new FinanceJourneyService().refreshInvoice('<sys_id>')` (or `refreshPayment`) in Scripts - Background, scope `x_695068_bcfa`.

**The exception lane stays open**

`journey_open_exceptions` > 0: open the exceptions list in the stage.

**There is no Playbook on a record**

1. Confirm the Playbook is active (Workflow Studio).
2. Confirm the record was created after activation (Playbook Executions `sys_pd_context`, `input_table` = the parent table).

**The workspace route shows a blank page**

1. Check the route URL form `/now/bcfa/playbook/<table>/<sys_id>`.
2. Check that the user has a BCFA role (the `bcfa.*` route ACL).

**A DRAFT payment does not clear**

`x_695068_bcfa.mock_sap.draft_outcome` is `pending` by default. Set it to `posted` and run Check SAP Draft Status.
