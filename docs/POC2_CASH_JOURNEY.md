## What runs where

| Step | Component | AI? |
|---|---|---|
| Bank payment arrives | `ArDomainService.intakePayment` (RECEIVED, customer unknown) | No |
| Upload remittance PDF, document type set at upload | Finance Document Intake, "Process Document" button | No |
| Read remittance fields | `SimulatedDocumentExtraction`: printed values of the fixture, labelled **SIMULATED** (Document Intelligence extraction not licensed/trained) | No |
| Link remittance to payment | Bank reference; only payments still in RECEIVED/NORMALIZED are processed | No |
| Customer identified | Remitter name via alias/exact name at or above `ar.match.auto_confidence` (0.95), else the single owner of every referenced invoice; anything else → `customer_ambiguous` | No |
| Open items loaded, match | `MatchingEngine.resolveRemittanceReferences`: each remittance reference → exactly one open item of that customer, same currency (never across currencies); fallback: exact amount, then greedy multi-invoice | No |
| Allocation and reconciliation | `ArDomainService.allocatePayment`: full open amounts; allocated − approved deductions must equal the payment (±0.01) | No |
| Multi-invoice explanation | Now Assist `ar_match_explanation` skill → `payment.ai_recommendation` (advisory, for the reviewer) | **Yes, advisory** |
| Exception | `ExceptionEngine.createArException`: severity, SLA, group BCFA Cash Application, owner, rule result, evidence, residual | No |
| Exception review | BCFA Cash Application Review workflow (Cash Match + Deduction Analysis agents) → advisory note with a residual classification | **Yes, advisory** |
| Reviewer decision | Approve Deduction / Request Clarification / Hold, mandatory reason (`ArExceptionDecisionService`) | No (AI identities refused) |
| Approval | `ArDomainService.routeForApproval` with `ar.approval.auto_approve_limit` (0: always human); requester ≠ approver | No |
| Clearing | Approval cascade → `IntegrationService` → Mock SAP clearing reference → open items settled → archive → CLOSED | No |

Settings (all **POC ASSUMPTION**, `src/fluent/config/policy_properties.now.ts`):
`ar.match.auto_confidence` 0.95, `ar.deduction.approval_threshold` 5,000 (larger deductions need a
finance approver), `ar.deduction.allowed_types` bank_charge, tcs, short_pay,
`ar.exception.high_value_residual` 5,000, `ar.exception.sla_hours`, assignment group and owner.

## Decision rules

| Decision | Who | From payment state | Result |
|---|---|---|---|
| Approve Deduction | `ar_processor` (≤ 5,000) or `finance_approver` | EXCEPTION, ON_HOLD | Short pay only; type chosen on the exception must be allowed; amount = computed residual (never typed). Deduction record (approved, approved by/at), balance re-checked, exception resolved, approval requested with the decider as requester |
| Request Clarification | `ar_processor` or `finance_approver` | EXCEPTION, ON_HOLD | Exception in review; payment ON_HOLD |
| Hold | `ar_processor` or `finance_approver` | EXCEPTION | Exception in review; payment ON_HOLD |

Every decision needs a reason of at least 10 characters, is refused for `identity_type = ai_agent`,
and writes a `human_decision` audit event.

## Defects found and fixed during verification

1. **Clearing never reduced AR open items.** Allocations were marked cleared, but the open items
   kept their full open amount and status, so a cleared invoice could be applied again.
   `ArDomainService._settleOpenItems` now settles them on clearing (and on reconciled unknown
   outcomes). Verified on all five POC 2 items.
2. **AR workflow note composition.** In case C the Cash Match agent read the trigger objective
   ("record an advisory recommendation") as a request to save and saved its own analysis; the
   orchestrator then finished without composing and saving the full note, so the Deduction
   Analysis agent's classification never reached the record, and that agent answered without
   calling its tools. Agent and workflow instructions were tightened (`02e54a6`: save only when
   explicitly given a note; always read context and the residual skill; delegate with "analyze
   only, do not save"; always save the composed note). **Retest** (`phase13c_retest_bg.js`, test
   case C1004 / ARINV4001, 29,975 vs 30,000): Cash Match read context + skill without saving,
   Deduction Analysis called both tools, one save of the composed note with the AI REVIEW header
   and "Classification: BANK_CHARGE, Amount: 25 INR". The test case was then closed through
   Approve Deduction and approval.

3. **A remittance that arrived after its bank line was refused (found in Phase 33).**

   **The problem.** Since the Phase 25 flows, the AR Payment Intake Flow processes a bank line as soon as it arrives. With no remittance yet, the customer cannot be identified, so the payment goes to EXCEPTION (`customer_ambiguous`) within seconds. Document Intake, however, still linked a remittance only to a payment at RECEIVED or NORMALIZED. Every late remittance therefore went to manual review, and the live cash journey above could no longer run.

   The AR Remittance Processing Flow already existed to retry such a payment. But it never got a remittance to work with. Its retry also went straight to MATCHING, which cannot match a payment that has no customer.

   **The fix (2026-09-29).**
   - Document Intake now also links a remittance to a payment in EXCEPTION, when that payment has an open `unmatched`, `customer_ambiguous` or `ambiguous_match` exception. Matched, cleared and closed payments are still never reopened.
   - `ArDomainService.retryWithRemittance` is used by the flow and by inline mode. It identifies the customer from the remittance with the same rules as `resolveCustomer`: an alias or exact name at the auto-match confidence, or the single owner of every referenced invoice. It does this without a state change, because EXCEPTION → CUSTOMER_RESOLUTION is not a lifecycle path. It then resolves the exception and retries matching through EXCEPTION → MATCHING.
   - If the customer still cannot be identified, nothing changes and the exception stays with the AR processor.

   **Verified live in flow mode** on RETEST data: customer C3301, invoice ARINV3301, payment BANK-P33-RT1.
   1. The bank line went to `customer_ambiguous` (AREX0001081).
   2. The remittance went through Document Intake (reading step stubbed, since there is no fixture PDF): linked and handed to the flows.
   3. The flow identified the customer from the remitter name, resolved AREX0001081, and matched and allocated ARINV3301, which put the payment at PENDING_APPROVAL with one pending approval.
   4. The payment was approved by `bcfa.finance.approver` (all five SoD checks passed), cleared and CLOSED.

   The test data is labelled RETEST and closed.
